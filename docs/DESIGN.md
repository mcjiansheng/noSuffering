# NoSuffering（不吃苦）
## 《杀戮尖塔 2》Mod 完整设计文档

设计版本：v1.3　｜　目标发行：v1.0　｜　日期：2026-10-08

**由房主控制的路线回滚、先古之民随机刷新与战斗重开工具。**

本文是开发与验收依据，替代此前的投票、直接选择、战斗中途洗牌和普通奖励刷新等旧方案。工程已基于 xht-rog 实际 public-beta v0.111.0 程序集实现；构建、加载与玩法验收分别记录于 docs/testing，不因源码实现而认定验收通过。

## 1. 产品范围与默认决策

### 1.1 五项核心操作

| 编号 | 游戏内名称 | 实际行为 | 费用 |
| --- | --- | --- | --- |
| F01 | 路线回滚 | 全队回到历史地图决策点，重新选择后续路线 | 永久免费 |
| F02 | 刷新先古之民 | 全队随机更换先古之民，生成新对象的初始选项 | 免费／扣血 |
| F03 | 刷新先古之民奖励 | 先古之民不变，全队各自重新随机奖励选项 | 免费／扣血 |
| F04 | 重新开始战斗 | 全队恢复战前状态，保留当前尝试的牌序 | 永久免费 |
| F05 | 重开并刷新牌序 | 全队恢复战前状态，重新随机每名玩家的初始牌序 | 永久免费 |

“奖励刷新”仅指先古之民内部奖励。更换先古之民时自带一次初始选项生成，只收取 F02 的费用，不再叠加 F03 的费用。

单人玩家视为房主。多人局中只有房主能够发起以上操作，队友自动同步，不参与投票、不提交申请。单步战斗撤销作为可选兼容项，不是第六项必做功能，也不是运行本 Mod 的前提。

### 1.2 用于直接实施的默认值

以下参数是本文补齐的设计默认值，不视为用户已经逐项指定的数值。

| 事项 | 默认规则 |
| --- | --- |
| 扣血对象 | 单人扣自己；联机仅扣房主，不扣队友 |
| 两种刷新费用 | 独立配置，均默认免费；扣血金额预设各为 5 点，可修改 |
| 支付下限 | 支付后至少剩 1 点生命，否则不刷新、不扣血 |
| 历史数量 | 最近 10 个完整地图决策点，可设置数量 |
| 历史组织 | 线性历史；回滚成功后删除目标之后的检查点 |
| 候选规则 | 按当前模式、幕次和解锁条件获取合法先古之民，排除当前对象 |
| 领取限制 | 任意玩家提交本次奖励选择后，两种先古之民刷新均锁定 |
| 普通战斗重开 | 保留最近一次成功生成的牌序，而非强制回到最初牌序 |
| 历史刷新费用 | 随运行状态正常回滚，不建立不可退还的扣血账本 |

### 1.3 明确排除

不刷新普通事件、战斗奖励、商店、宝箱、普通遗物或药水；不提供指定先古之民、挑选奖励、查看未来牌序、指定起手或任意数值修改。

不做客户端权限申请、投票、费用分摊、金币收费、次数收费、分支存档树或战斗中途重洗。v1.0 不自行开发逐动作回放引擎，不为尚未实现的功能建立插件平台。

## 2. 快捷面板与设置

### 2.1 基本交互

默认 F6 打开／关闭面板，Esc 关闭。支持在设置中重新绑定按键或组合键。只处理按下事件，忽略长按重复；聊天、文本框输入和快捷键录制期间不触发玩法操作。

面板采用原生 Godot 控件，跟随游戏缩放，提供简体中文并预留英文。打开面板只拦截本地点击穿透，不暂停其他玩家的游戏；真正提交全队操作时才短暂锁定相关输入。

| 场景 | 显示内容 |
| --- | --- |
| 地图或其他稳定房间 | 路线回滚、历史检查点 |
| 未确认奖励的先古之民界面 | 刷新先古之民、刷新先古之民奖励、可展开的路线历史 |
| 战斗中 | 两种战斗重开、可展开的路线历史 |
| 奖励已提交 | 刷新按钮置灰，提示“已有玩家确认奖励” |
| 加载或操作同步中 | 显示当前状态，不接受新操作 |
| 非房主客户端 | 提示“本局由房主控制”，仅查看状态和调整个人设置 |

路线回滚不限定在地图界面使用。存在有效检查点、且到达可恢复的动作边界时，房主可以从战斗等场景直接返回历史选路点。

### 2.2 面板信息结构

```text
不吃苦 · NoSuffering                  [设置] [关闭]
联机：房主控制                       当前：战斗

[重新开始战斗]                          免费
  恢复全队战前状态，保留本次牌序。

[重开并刷新牌序]                        免费
  恢复全队战前状态，重新随机每人的牌序。

[路线回滚 ▾]
  第 2 幕 · 第 8 层结算后 · 待选下一节点
  第 2 幕 · 第 7 层结算后 · 待选下一节点
```

费用直接写在按钮旁，例如“房主支付 5 点生命”。队友通过简短通知获知房主操作，不必打开面板。

路线回滚默认只弹出一次确认，写明目标与将被撤销的进度。战斗重开和刷新默认直接执行。刷新成功后尽量保持面板打开；房间重载时自动关闭，加载完成后恢复快捷键。执行中禁用重复点击。

### 2.3 游戏内设置

标准使用组合为 NoSuffering 与 ModConfig。设置注册到 ModConfig 页面，面板中的设置按钮打开同一页面。ModConfig 已提供快捷键、开关、下拉框和数值配置，并支持通过反射软依赖接入。[R5]

核心功能不强制依赖 ModConfig；未安装时使用默认值和本地配置文件，设置入口提示安装 ModConfig。发行说明将其列为游戏内设置界面的推荐前置，不再开发第二套完整设置系统。

## 3. F01：路线回滚

### 3.1 检查点的准确含义

检查点是**上一房间处理完毕、下一节点尚未确认进入的地图决策状态**。它不是地图坐标，也不是一个已经领取过奖励但未同步其他状态的房间截图。

例如，第 8 层结算后选择了第 9 层精英战。回到“第 8 层结算后”，应保留第 8 层及以前的全部结果，撤销第 9 层及之后的变化，并允许重新选择第 8 层的合法出边。

同一决策点只记录一次，在进入下一节点前最终封存。第一条检查点以本局首次真实到达的地图决策状态为准，不伪造尚未到达的起点。

### 3.2 恢复内容

恢复全队生命、生命上限、金币、卡组及永久卡牌属性、遗物及计数、药水与槽位，以及幕次、地图、路线、房间历史、事件和奖励处理状态、相关池状态与原生 RNG。

同步恢复该历史位置的 Mod 数据，例如刷新计数与战斗尝试记录。个人设置、房主玩法配置和网络操作序号不跟随游戏时间线回滚。

使用原生运行状态序列化和加载能力；原生格式未覆盖但影响玩法的状态由适配层补存。恢复通过原生房间／运行重建流程完成，不逐个修改当前场景中的生命、金币和坐标来模拟回滚。

### 3.3 历史管理

默认保留最近 10 个完整检查点，展示幕次、层数、上个房间类型、全队生命摘要和创建时间。成功回滚后截断目标之后的历史，新路线继续追加；不保留可切换的平行分支。

最近检查点可以跨幕保留。跨幕恢复须一并重建对应幕的地图与生成状态，不能只切换幕编号。目标必须属于当前局、相同玩家阵容和兼容版本；验证成功、实际加载完成后才截断历史。

### 3.4 免费与回退语义

回滚不额外扣除任何资源，也没有收费开关。回滚点之后获得的奖励被撤销，消耗的药水恢复，之后支付的刷新生命按快照恢复；不增加防刷、追缴或不可退款账本。

原地图不因回滚重新生成。改走其他路线、采取不同操作后，后续进程可以自然变化，但不额外冻结所有未来随机结果。回滚只处理本局运行状态，不改写账号解锁、平台成就或全局统计。

## 4. F02 / F03：先古之民刷新

### 4.1 共同条件

房主处于先古之民事件，且全队尚未提交本次奖励选择时可用。任何玩家提交奖励选择，即使仍在后续选卡、变换或目标选择流程中，也立即锁定两种刷新。悬停和未提交的本地高亮不算确认。

回滚到确认前的完整检查点后，按恢复后的状态重新判断可用性；不额外保存“曾经领取过所以永远禁用”的标记。

### 4.2 刷新先古之民

获取当前合法候选，排除当前对象，再按游戏的候选规则和权重随机抽取替代对象。不提供选择列表，也不把所有奖励一次性展示出来。

全队使用同一个新先古之民，各玩家的奖励按各自条件生成。切换必须更新事件模型、运行状态和 UI，清理旧按钮及回调，不只是替换名称和头像。

当前入口只有一个合法对象时，显示“没有可替换的先古之民”，不收费、不推进计数。v1.0 不为突破这一条件额外实现跨入口先古之民移植。

### 4.3 刷新内部奖励

保持先古之民不变，为每名玩家重新随机自己的奖励选项，保留原本数量、角色限制及合法性条件。不把房主的结果复制给所有队友。

允许新旧选项部分甚至全部相同；完成一次有效重抽就按次计费，不保证结果更好。生成失败、对象已失效或不存在可生成结果时不收费。

### 4.4 一次操作只提交一次

扣费、新先古之民或选项、随机计数和必要的奖励池变化作为同一操作提交。先检查条件并生成有效结果，再统一生效；失败时保留或恢复提交前状态。

刷新期间暂时锁定全队的奖励选择。领取和刷新在同一个执行边界排序：领取先提交，刷新取消且不扣血；刷新先提交，旧选项请求失效，玩家面对新选项重新选择。旧界面的“选项 1”不得误领新界面的“选项 1”。

事件重建不重复累计入场收益，也不能因替换未领取选项而反复消耗唯一奖励池。界面打开、悬停和重绘不调用玩法随机生成逻辑。

## 5. 费用规则

两种先古之民刷新分别配置 Free 或 Hp，各自有独立金额。路线回滚和两种战斗重开永远绕过费用逻辑，不定义收费字段。

设房主当前生命为 H，费用为 C。Hp 模式下 C 是正整数，只有 H > C 才执行，成功后当前生命为 H − C。生命不足则不扣血、不刷新，不截断费用，不允许刷新致死。

费用只扣当前生命，不减少上限，不从队友分摊，不受格挡抵消。它是系统费用，不模拟攻击伤害或额外触发战斗受伤收益；使用同步的状态更新路径更新 UI 和存档。

Free 模式忽略金额字段。设置变化在当前操作结束后生效，进行中的操作始终使用开始时的房主规则。

同一事件内连续刷新要保留已支付生命；普通退出重进、界面重建和客户端重连不能退款。只有主动回滚到付费之前的历史状态，才自然恢复当时的生命。

生命已经存在运行快照中，不按刷新计数重新计算或补扣费用。重复消息、重复回调只应用一次操作；失败时生命、选项、奖励池和计数一起保持原状或恢复。

## 6. F04 / F05：战斗重开

### 6.1 不可变战前基线

每场战斗建立一个战前基线 B，包含全队入场状态、已确定的遭遇描述，以及原生初始化需要的随机状态。捕获位置在开场效果和起手抽牌之前，同时已能确定本场遭遇，避免重开时重抽敌人。

原生保存时机不完全匹配时，由适配层补足遭遇或初始化数据，使最终恢复满足同一语义。不把已抽完起手牌的第一回合状态当作战前基线。

两种重开都从 B 重建全队战斗。战斗内受伤、药水消耗和临时变化被撤销；战前已有的资源变化保留，包括先古之民刷新费用。敌人组合与战前资源不变。

### 6.2 当前尝试记录

每场战斗维护当前尝试 A。首次进入为 A = 0；每次成功刷新牌序切换到新的尝试记录。普通重开不改变 A。

| 操作 | 预期结果 |
| --- | --- |
| 首次进入后普通重开 | 从 B 重现尝试 0 |
| 刷新牌序后普通重开 | 从 B 重现刚生成的新牌序，不退回尝试 0 |
| 连续两次刷新牌序重开 | 恢复同一 B，但采用两个新的尝试记录 |
| 新牌序战斗退出重进 | 保留当前尝试，不自动重新随机 |
| 回滚至更早路线 | 按恢复后的运行状态建立或恢复相应战斗记录 |

普通重开恢复当前尝试的完整初始化随机条件，目标是在采取相同操作时可复现。刷新牌序只为初始牌序添加新随机输入，不重抽敌人或战后奖励。

### 6.3 初始牌序约束

房主统一分发操作和随机输入，每名玩家分别重排自己的牌序。保持卡牌组成、数量、永久属性和原版固有、固定起手等限制。随机牌序可能产生相同起手，不承诺每次都不同。

不在战斗中途搬动手牌、弃牌或消耗堆，不撤销一次抽牌，也不额外触发一次洗牌效果。跨重开允许原生系统重建运行时卡牌对象，要求一致的是逻辑卡牌及属性，不是旧对象引用。

开场遗物、能力和抽牌效果在恢复后的新战斗中正常执行一次；不得在未恢复前置状态的情况下重复累计开场收益。

### 6.4 操作边界

活动战斗中可用，等待当前已提交动作到达原生可恢复边界后执行。单名队友阵亡但战斗尚未结束时，仍允许全队重开。

v1.0 的必验收入口为活动战斗。全队战败结算页重开留作复用同一基线的后续增强，不为它新增死亡拦截或全局统计回滚。胜利进入奖励领取阶段后隐藏两种重开，需要反悔时使用路线回滚。

## 7. 随机数设计

### 7.1 独立的刷新输入

保存原生 RNG 状态，为主动刷新使用独立、可持久化的随机输入。不开新的全局游戏种子，不让各端用系统时间自行随机，也不让界面行为消耗玩法随机数。

输入区分本局、上下文、功能域、刷新次数和玩家。例如：

```text
先古之民：RunId + AncientContextId + AncientRerollIndex
内部奖励：RunId + AncientContextId + OptionsRerollIndex + PlayerId
战斗牌序：RunId + CombatId + ActiveAttempt + PlayerId
```

这些是本 Mod 的设计字段，不是游戏已有 API。使用稳定编码、稳定哈希和确定性随机算法，不使用进程相关的字符串 GetHashCode 作为种子。房主记录实际输入，客户端应用或确定性重建同一结果。

### 7.2 牌序补丁的优先路线

保留原版初始洗牌对原生 RNG 的正常消耗，在起手抽牌之前，用 Mod 私有随机输入重排允许变化的部分。只替换初始牌序输出；后续洗牌恢复原版逻辑。

具体插入点先从当前程序集确认洗牌、固定起手处理和首张抽牌的执行顺序，再做窄范围补丁。各端从同一规范顺序开始，对相同逻辑卡牌和限制执行一致算法，并核对牌序摘要。

不采用覆盖全场的全局 RNG 补丁，不为刷新牌序重新创建角色卡组，不把额外洗牌事件发送给遗物和能力。

### 7.3 干预范围

“只刷新牌序”限定 Mod 直接改变的对象。新起手可能改变开场互动与后续操作，从而自然改变后续随机消费；不要求剩余整场结果永远与旧尝试相同。

先古之民生成结果涉及的奖励池和事件状态仍按游戏规则更新并保存。独立 RNG 不等于跳过这些状态变化。

## 8. 联机同步

### 8.1 房主权限

所有玩法入口都检查实际房主身份，不能只隐藏客户端按钮。全员安装相同发行版本的 NoSuffering，并使用游戏允许的兼容玩法 Mod 组合。客户端个人按键、语言等设置不改变房主规则。

房主控制是本 Mod 的授权方式，不代表只改房主内存就能完成联机。客户端仍需执行一致的动作顺序、随机状态更新或原生加载流程。

### 8.2 统一执行流程

```text
房主触发 → 校验场景、身份、目标及费用
         → 到达原生动作边界，短暂锁定相关输入
         → 分发同一操作标识与结果／随机输入
         → 全端执行刷新或运行状态恢复
         → 校验并保存，恢复输入
```

复用原生可靠通信、动作队列、加载完成通知和重连方式，不另造服务器或通用分布式事务框架。程序自动确认加载完成，不要求玩家点击同意。

原生加载需要返回房间、重新加入或显示加载画面时，采用现成流程；不把“必须无黑屏”设为交付条件。

### 8.3 最少必要数据

| 逻辑数据 | 用途 |
| --- | --- |
| RunId / SessionEpoch | 区分当前局和会话，拒绝旧会话消息 |
| OperationId / WorldRevision | 操作去重，拒绝回滚前的过期命令 |
| CommandType / ContextId | 区分五种操作及其房间、事件或战斗 |
| CheckpointId / AttemptId | 指明目标检查点或战斗尝试 |
| ResultPayload | 新先古对象、各玩家选项或随机输入 |
| RulesRevision / Cost | 固定本次房主规则与费用 |
| StateDigest | 检查相关玩法状态是否一致 |

这些是逻辑契约，可复用原生字段，不要求逐项新造协议。网络控制序号不属于游戏历史；恢复旧检查点时，WorldRevision 仍向前推进，防止旧消息重新生效。

### 8.4 加载、身份和断线

使用原生多人加载路径，保持每个客户端映射到自己的玩家；不把房主单人存档直接分发为所有人的存档。RestartCombat 提供房主发起全队战斗重开的公开参考，其更新记录也涉及多人存档加载路径修正。[R2]

重连时同步已提交的当前状态、尝试记录与规则，不用客户端旧计数重新随机。恢复时有人断线，沿用原生连接处理，不让部分客户端继续旧战斗。本 Mod 不新增主机迁移系统。

提交前验证失败，不改变状态；提交后发生状态分歧，统一通过原生加载／重连回到已确认的有效状态，不靠零散改字段继续运行。

## 9. 存档与状态管理

### 9.1 保存对象

游戏快照必须是独立、不可变的数据，不保留仍会被当前战斗修改的对象引用。

| 对象 | 内容 |
| --- | --- |
| RunEnvelope | 原生运行状态、版本、玩法 Mod 指纹、玩家映射和摘要 |
| MapCheckpoint | RunEnvelope、地图决策描述、历史序号、对应 Mod 数据 |
| CombatBaseline | 战前状态、确定遭遇和初始化信息 |
| CombatAttempt | 当前尝试编号、各玩家初始牌序输入及摘要 |
| AncientState | 事件上下文、两种刷新计数、当前结果及领取状态 |
| LocalConfig / HostRules | 与游戏历史分离的个人配置和房主规则 |

### 9.2 保存时机与持久化

新地图决策点、先古之民刷新完成、确认新战斗尝试、回滚完成及原版正常存档时保存对应 Mod 数据。战前基线每场建立一次，不让普通重开或新牌序重开覆盖成受伤后的状态。

优先使用原生 Mod 存档扩展入口；没有合适入口则使用按 RunId 隔离的伴随文件。原生存档与 Mod 数据使用同一提交标识配对，包含格式版本和校验信息，不混合新存档与旧尝试记录。

伴随文件先写完整新版本，再原子切换索引。历史快照主要由房主持有，客户端保存／同步原生重连所需的个人化状态和当前 Mod 记录。

检查点超限时清理最旧历史，保留当前有效战前基线。不每帧复制状态，不因打开面板或无效点击增加快照。

## 10. 工程设计

### 10.1 技术基线

采用 C#、原生 Mod 加载入口、Harmony 与 Godot UI。目标框架、Godot 和补丁库版本以 xht-rog 实际安装为准，优先引用同一安装中的对应程序集。

社区环境教程要求检查 release_info.json、sts2.runtimeconfig.json 和游戏程序集，并以安装文件确定兼容基线；不应把教程示例版本当作当前机器版本。[R1]

只读分析游戏程序集，不修改本体。不把游戏 DLL、资源包和反编译的游戏源码提交到仓库或发行包。Manifest 正确声明改变玩法，但不能把该声明当作联机同步实现。

### 10.2 模块边界

| 模块 | 职责 |
| --- | --- |
| GameBridge | 包装具体游戏版本的序列化、加载、事件生成、洗牌和联机入口 |
| CheckpointService | 线性地图历史、战前基线与恢复 |
| AncientService | 两种刷新、费用与统一结果 |
| CombatRestartService | 重开、尝试管理与初始牌序替换 |
| HostCoordinator | 房主鉴权、排序、去重、同步与完成确认 |
| Overlay / Config | 面板、输入、文案、ModConfig 桥接和配置持久化 |
| UndoCompatibility | 只为真实支持的外部撤销实现提供适配 |

GameBridge 保持为薄适配层。费用是先古之民模块的小组件，不另造经济系统。目录按责任组织即可，不要求每个名词创建接口、工厂和依赖注入层。

### 10.3 集中确认四组真实入口

调查只围绕地图保存与多人加载、先古模型与选项生成、战斗初始化与起手洗牌、原生联机提交与加载完成四组入口展开。

本文中的类名和字段属于项目设计，不是已核实的游戏方法名。Codex 从实际 DLL 确认签名和调用时机，记录在代码旁或简短接口说明中，不先编写大型逆向报告。

## 11. 战斗撤销与其他 Mod

NoSuffering 自己实现整场战斗重开；单步撤销可直接与已有 Mod 共存，或通过已支持的接口提供入口。没有公开调用接口时，不靠模拟按键或修改对方私有字段伪造集成。

设置提供 Off 和 Auto；仅显示已经完成并验证的适配器，不显示空提供者。StS2 Undo 的作者说明当前面向单人模式，因此其公开能力不能直接视为现成的联机单步撤销方案。[R4]

路线回滚或重开后，旧战斗撤销历史必须随生命周期销毁或通过适配器清空，不允许把已丢弃战斗的状态、牌序或 RNG 回灌到新尝试。没有联机适配器时，不显示 NoSuffering 的外部撤销入口，五项核心功能照常工作。

RestartCombat 的仓库标示 MIT，可在实际许可范围内复用代码并保留署名。[R2] Refresh Ancient 已展示两种刷新并记录作者的多人测试，但发布页对修改和素材使用要求先获许可，因此仅作为行为参考，不直接复制其发布文件。[R3]

对同一加载或洗牌入口的冲突，以具体组合测试结果说明，不声明“兼容所有 Mod”，也不擅自修改其他 Mod 的配置。

## 13. MacBook 与 xht-rog

**MacBook 用于编辑和操作 Codex；xht-rog 负责游戏文件、最终构建、部署与实机测试。** 复用现有远程访问，不重新搭建网络，也不要求 MacBook 安装游戏。

通过已授权的远程终端或脚本执行版本检查、构建和日志采集，画面检查使用现有远程桌面。代码采用一个明确的主工作目录或 Git 仓库，实际游戏路径写入本地配置，不硬编码进源码。

只需提供可用远程执行入口和游戏路径，凭据仍由现有工具管理，不写进文档或仓库。Mac 上编译通过不能替代 xht-rog 上加载和联机测试。

### 13.1 版本和常用 Mod 兼容要求（v1.3）

同时面向最新 public-beta 与正式版，优先适配 beta。以实际安装、Steam 分支构建和程序集指纹为依据，不用发行名称推测 API 相同。构建脚本分别接受各版本安装目录；没有对应程序集的分支记录为未构建，不切换用户当前 Steam 分支来冒充验证。

常用组合优先核查 BaseLib、ModConfig、UndoAndRestart、RitsuLib、MintySpire2、意图显示和卡牌平衡类 Mod。保留它们的原生开场、固有、牌序修改和渲染钩子；只在初始洗牌中插入 NoSuffering 的输出。无法恢复的第三方事件状态应限制该场重开并说明，不应破坏普通进入战斗。

单步撤销适配保持可选。重复重开、事件刷新类 Mod 的历史清理需要实际组合验证，未验证不能宣称全面兼容。跨版本伴随存档不自动迁移，避免将旧版本初始化数据拼入新运行。

## 14. Codex 实施与交付

### 14.1 三个连续批次

| 批次 | 可验证产物 |
| --- | --- |
| A：建立闭环 | 按真实 DLL 创建工程；面板与配置；单人和房主发起的全队普通重开 |
| B：完成回退 | 地图检查点和回滚；新牌序重开；当前尝试的保存与重现 |
| C：完成核心 | 两种先古刷新及费用；领取互斥；持久化、重连与联机回归 |

从 A 起使用联机架构，不先写单人专用方案再重构。可选单步撤销适配在核心完成后进行，不阻塞版本交付。

### 14.2 执行要求

Codex 连续调查、编码、构建和验证，不因每个类、按钮或补丁暂停询问。优先完成实际可用的游戏路径，不用空实现、假按钮或大段设计代替功能。

API 不符时直接检查对应程序集并调整适配层。常规技术选择自行推进；只对确实缺少的权限和不可替代环境提出具体需求，同时继续完成独立工作。

项目根目录 AGENTS.md 仅保存简短约束，完整需求放入 docs/DESIGN.md。OpenAI 文档说明 Codex 会读取 AGENTS.md 作为项目指导，无需每轮重新粘贴完整需求。[R6]

### 14.3 交付物

完整源码、可安装 Mod 包、必要的构建和部署脚本、配置示例、安装使用说明，以及真实测试记录。确有资源需要时才增加 PCK，不为纯代码 UI 强制建立资源工程。

记录游戏构建、Mod 版本和实际验证范围；构建、加载、单人、双人及满员测试分别标注。未执行的测试写“未执行”，不以编译成功、作者说明或未出现异常日志代替实测。

发行包不包含游戏本体文件，实际复用的第三方代码保留必要许可与署名。

## 15. 验收标准

### 15.1 核心机制

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| T01 | 回到选精英前的分叉口 | 全队资源和路线正确恢复，允许重新选路 |

| T10 | 普通重开 | 全队恢复战前资源，当前尝试可复现 |
| T11 | 刷新牌序后普通重开 | 保留刚生成的牌序，不回到初始尝试 |
| T12 | 固有和固定起手 | 规则保留，卡牌数量属性不变，无额外洗牌触发 |

### 15.2 联机与存档

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| T13 | 非房主调用入口 | 不产生玩法变化，鉴权不只在 UI 层 |
| T14 | 重复消息和连续点击 | 一次操作只生效、扣费和推进计数一次 |

**v1.0 完成标准：五项操作在单人和多人局可用，房主权限、费用、完整恢复、保存／重载与当前尝试语义通过测试。单步撤销和战败结算页重开不阻塞核心交付。**
